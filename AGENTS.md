# AGENTS.md

Guidance for future agents working in this repository.

## Project Snapshot

- This is a Flutter app named `shadchan`, a Hebrew RTL shidduchim management app.
- The current Dart source layout is intentionally simple and flat:
  - `lib/models/` - Hive data models and generated adapters.
  - `lib/providers/` - `ChangeNotifier` repositories for people and matches.
  - `lib/screens/` - top-level app screens and flows.
  - `lib/services/` - backup/import, contacts import, incoming files, notifications.
  - `lib/utils/` - routing, theme, enums, formatting, phone/share/name helpers.
  - `lib/widgets/` - reusable UI widgets.
  - `lib/dialogs/` - reusable dialogs and sheets.
- App entry points are `lib/main.dart` and `lib/app.dart`.
- Navigation is centralized in `lib/utils/app_router.dart` using `go_router`.
- Tests live under `test/`, with service tests in `test/core/services/` and the app boot test in `test/widget_test.dart`.

## Product Rules

- All user-facing UI text must be Hebrew.
- Keep the app fully RTL. `lib/app.dart` wraps the app in `Directionality.rtl`; new screens and widgets should fit that assumption.
- Preserve local-first behavior. User data is stored locally with Hive, local files, and explicit import/export flows.
- Be careful with privacy-sensitive features: contacts, photos, sharing, backup JSON files, and notifications.
- If a task is unclear or has a meaningful product/technical choice, ask before proceeding.

## Platform Rules

- Keep the minimum platform intent aligned to Android 21 and iOS 15.5 unless the user explicitly approves a change.
- iOS deployment target is set to `15.5` in `ios/Runner.xcodeproj/project.pbxproj` and in `ios/Podfile`. The floor is forced by the dependencies, not by choice: the Firebase pods require 15.0 and `google_mlkit_face_detection` requires 15.5. Both files must be changed together.
- iOS bundle identifier is `com.gilad.shadchan`, matching the Android `applicationId`. It is also the identifier the Firebase iOS app is registered under, so changing it means re-running `flutterfire configure`.
- `ios/Podfile` is hand-written (Windows `flutter create` never generates one). Its `post_install` block sets the permission_handler compile flags: only `PERMISSION_PHOTOS=1`, everything else `0`, so the binary carries no API references without a matching usage description in `Info.plist`. Adding a new `permission_handler` permission means adding both the flag and the plist string.
- Android uses the Flutter Gradle values in `android/app/build.gradle.kts`; do not raise the effective min SDK casually.
- **The Android build needs JDK 21, and the machine has to be told twice.** Gradle 8.14 embeds a Kotlin compiler whose `JavaVersion.parse` does not understand a JDK 25 version string, so compiling the `.kts` build scripts under Android Studio's bundled JBR (25.0.2) dies in the configuration phase with a "What went wrong" that is *only* the version number — `java.lang.IllegalArgumentException: 25.0.2`, with no other clue and no mention of Java. It fails in about a second and only when the compiled-script cache is cold, which is why an APK build can pass while `flutter build appbundle` fails on the same tree, and why building from a terminal whose `JAVA_HOME` is already 21 hides it completely. The reproduction that removes all doubt is `JAVA_HOME=<Android Studio>/jbr ./gradlew help` — no compilation, same failure.
  - **`org.gradle.java.home` in the user-level `~/.gradle/gradle.properties` is the fix that actually holds.** `gradlew` picks its JVM from the ambient `JAVA_HOME`, and Android Studio exports its own JBR to every process it spawns, so nothing on the Flutter side can reach it. This file is outside any repo (no machine path gets committed), applies however the build is launched, and affects every Gradle project on the machine — which is the intent, but is also why it is worth removing once Gradle is new enough for JDK 25.
  - `flutter config --jdk-dir=...` is *also* set, and is worth keeping — it is what Flutter's own tooling (`flutter doctor`, the Java it hands to Gradle) uses, and Flutter's order is `--jdk-dir` → **Android Studio's JBR** → `JAVA_HOME` → `PATH`, so without it the JBR beats a perfectly good `JAVA_HOME`. But on its own it does **not** fix the build, because it never reaches the JVM `gradlew` chooses for the daemon. Do not stop at it, as one earlier pass did.
  - AGP 8.11.1 and Gradle 8.14 support JDK 17–21 and nothing newer. Expect this to come back every time Android Studio updates its JBR, and after a fix restart Android Studio so no daemon from the old JVM is reused.
- Android release builds use `android/app/proguard-rules.pro` and `android/app/src/main/res/raw/keep.xml` for notification/Gson/R8 safety.
- Native file-open backup import is wired through:
  - Android: `android/app/src/main/kotlin/com/gilad/shadchan/MainActivity.kt` and `AndroidManifest.xml`.
  - iOS: `ios/Runner/IncomingBackupFileBridge.swift`, `SceneDelegate.swift`, and `Info.plist`.
- Share-into-app on iOS is the `ShareExtension` target (`ios/ShareExtension/`). It runs in its own process, so the share is handed over through the app group `group.com.gilad.shadchan` — `ios/Runner/SharedProfileInbox.swift` owns that layout and is compiled into *both* targets. The extension writes image files first and the `payload.json` manifest last; the app only reads directories that have a manifest, so a half-written share is never imported. The extension then opens the app with the `shadchan-share://` scheme. Changing the app group id or the scheme means changing both entitlements files, `SharedProfileInbox.swift`, and `Runner/Info.plist` together.
- The drafts the extension produces go through the *same* `shadchan/incoming_shared_profiles` channels as the Android `SEND` intents, in the same `{id, text, filePaths}` shape, so no Dart code is platform-specific.

## Development Workflow

- Read this file before starting work and update it after meaningful project changes.
- Prefer the existing folder structure before adding new layers.
- Keep generated Hive files (`*.g.dart`) in sync when changing Hive models/enums:
  - `flutter packages pub run build_runner build --delete-conflicting-outputs`
- Run targeted checks first, then broader checks when the change touches shared behavior.
- Useful verification commands:
  - `flutter analyze`
  - `flutter test`
  - `flutter build apk --debug`
  - `flutter build apk --release` for release/platform-sensitive changes.
- iOS native compilation is not normally verifiable from this Windows environment; mention that when relevant.

## Current Capabilities To Preserve

- People management: list, search/filter/sort, add/edit/detail, favorites, gallery photos, sharing, delete warnings.
- Matches management: list, create, duplicate detection, detail, status/handler updates, notes timeline.
- Dashboard tab at `/dashboard`.
- Contacts import: explicit permission-on-entry flow, search by name/phone, multi-select import, duplicate blocking by normalized phone.
- Unified add-contacts screen at `/people/import` with toggle between swipe (default) and list views; legacy `/people/swipe` redirects to it.
- Local JSON backup/export/import from Settings.
- Open-with-app backup import for JSON backups.
- Share-to-app intake for shidduch details from WhatsApp/other apps: Android accepts text, image, or image+text shares; iOS accepts image open-with through document handling. The flow asks whether to create a new person or add to an existing person, then opens `PersonFormScreen` with the shared text in `כרטיסייה לשליחה` and shared images staged as unsaved photos.
- Birthday notifications using local timezone support.
- Hebrew privacy policy screen and Settings entry.
- Optional Google Sign-In from the profile's `החשבון שלי` section, upgrading the anonymous Firebase account in place.
- Cloud backup to Firestore + Cloud Storage while signed in, running on app open and close, with an explicit additive restore. Covers people, matches, both note kinds, the matchmaker's own profile, and every photo file.
- Store update check on app open and on resume, offering the new version through a Hebrew dialog that links to the store listing.

- 2026-08-19: **A one-time sign-in screen, and the community gated behind it.** Signing in was previously one row in the settings that almost nobody found; it is now a step in the entry flow that every matchmaker sees exactly once, and the thing it unlocks is visible from the home screen.

  **The gate is a local flag, and it has to be.** `SignInPromptStore.hasAnswered` decides whether a launch opens on `/sign-in`, and it is read from the router's `redirect` — which runs on the *first frame*. Answering "is somebody signed in?" honestly means `Firebase.initializeApp`, App Check and the auth restore, which is precisely the cold-start cost `FirebaseBootstrap` exists to avoid. So the flag is written when the question is answered, **either way** — signing in and skipping both set it, because a screen somebody declined must not come back next launch. The one case a local flag gets wrong is a matchmaker who connected an account in an earlier version: `SignInScreen` watches `AccountProvider` and takes itself out of the way when `isSignedIn` turns true, which costs them one screen for the moment Firebase takes to answer.

  **`/sign-in` is not bounced back once answered**, because the "התחברות" buttons on both community surfaces push the same screen. It pops when it can and goes to `/home` when it cannot, which is the difference between the entry-flow life and the pushed-from-a-card life.

  **Apple goes through `AppleAuthProvider`, not a plugin, and only on iOS/macOS.** No new dependency, no Podfile change, one code path. `AccountService.isAppleAvailable` is `Platform.isIOS || Platform.isMacOS`: on Android `signInWithProvider` falls back to Apple's *web* flow, which needs a Services ID and a return URL in the Apple Developer portal and the Firebase console, and until they exist the button opens a browser that ends on `invalid_client`. Turning Android on later is that one getter plus the console work. **`ios/Runner/Runner.entitlements` gained `com.apple.developer.applesignin`** — required for the native sheet, and required by App Store review wherever Google sign-in is offered.

  **`CommunityService._account()` now refuses an anonymous uid, and that one check is the whole gate.** Every device has an anonymous account from first launch — it is what App Check and the AI quota hang off — so accepting it is what used to put matchmakers who had never signed in into the community totals and onto the leaderboard, under a uid that dies with the install. The publish, the totals and the board all go through `_account()`, so they were all fixed at once, and a signed-out device simply reads zeroes without touching the network.

  On the surfaces: the home block keeps "הפעילות שלך" and its שבוע/חודש/כל הזמנים switch and replaces the community column with `CommunitySignInCard.joinTheCommunity`; `/activity` keeps both personal cards and replaces the two community sections with `CommunitySignInCard.communityIsForMembers`. **Their own numbers are never withheld** — the gate is about the community, not about anything that was ever theirs.

  **First sign-in restores, then syncs, and that order is the one that loses nothing.** `CloudSyncService.restore` only ever adds (an id that exists locally is left alone; the profile fills empty fields only), so it cannot overwrite this phone. `syncNow` then pushes the union against an empty fingerprint ledger, and an empty ledger means an empty `removed` list, so nothing already in the account is deleted either. A matchmaker with a database here and a database there ends with both. It runs unawaited from `SignInScreen`: it is a backup, and they should be on the home screen while it happens.

  **The reminder afterwards is paced in friends, not in days.** `SignInPromptStore.shouldRemind` fires once at 25 friends and not again until 75 more — somebody who has not added anybody has not acquired a new reason to be asked, however long ago it was. It sits **last** in `CommunityPromptGate`, below everything else, because it is the only prompt there that re-asks something already declined. The gate also skips `LeaderboardConsentDialog` and the whole network branch for a signed-out device: asking somebody who is not in the community whether their name may appear in it is a question about nothing.

  **Every widget test that boots the app now needs `settings.put('signIn.promptAnswered', 'true')`** in its `setUpAll`, or it opens on the sign-in screen instead of the shell. `SignInPromptStore.resetForTest()` exists because the write-through `_pending` cache is static and outlives the Hive box a test clears between cases.

  `PRIVACY_POLICY.md`, `privacy_policy_screen.dart` and `privacy_overview_screen.dart` all now say that the community area is for signed-in users only and that nothing is published without an account.

  **Console steps outstanding, none of which live in this repository:** enable the **Apple** provider in Firebase Authentication; enable **Sign in with Apple** for the App ID in the Apple Developer portal; and, only if Android Apple sign-in is ever wanted, a Services ID and return URL. **Unverified from here:** no Apple sign-in has ever run — the flow is written and not exercised — and iOS native compilation remains unverifiable from Windows. - 2026-08-19: **The activity area was rebuilt around weighted points, taken out of the settings, and put on the home screen as two numbers.** The old version counted flat "פעולות", lived behind `הפרופיל שלי`, and showed a shared weekly goal, a personal weekly record and four community figures nobody had asked for.

  **A status update is no longer activity, and that is what makes the weights possible.** `ActivityStats` now counts four events — a friend added (1), an idea opened (1), a couple who started going out (5), an engagement or wedding (50) — through the new `ActivityBreakdown`. Status changes were the one countable thing in the app that cost nothing to produce, so weighting the rest while leaving them in would have rewarded tapping; both the `MatchStatusEvent` and the `PersonEvent` branches are gone. Engagements and weddings are **one event** (there is no `מאורסים` status) and are counted *in addition to* the five the couple already earned, dated from the first `toStatus == married` event and falling back to `updatedAt` for the couples who married before the ledger existed on 2026-08-14. Couples come from `DatingHistory` rather than a private copy of the 24-hour rule, so the five points and "זוגות שהוצאת לדייט" can never disagree about what a couple is.

  **The personal weekly record is gone, and `bulkImportLimit` went with it.** The record was the only reason an import of more than thirty friends was ever discounted, so an import of thirty is now thirty points everywhere — which is what the product actually wanted. `CommunityProfileStore.bestWeek`/`recordWeek`, `ActivityTotals.weekForRecord`, `CommunityMemberCounts.weekForRecord`, `ActivityStats._oversizedBatches` and the `record.week` achievement are all deleted. **`Person.importBatchId` (Hive field 40) was deliberately kept** and is still stamped by the AI import: it is persisted user data carried in the backup format, and removing a Hive field to delete an unused read is the wrong trade. `CommunityGoal` and the whole `communityGoals` collection are deleted too — its rules block is gone from `firestore.rules`, so old installs writing there now fail silently, which is what they already did on error.

  **The server fields are called `*Actions` and hold points. Do not rename them.** `weekActions` and its three siblings are the fields four composite leaderboard indexes sort by; renaming them to `*Points` would mean rebuilding all four and a window in which every board in the wild returns nothing. `CommunityPeriod.fieldPrefix` is what makes the other four per-window fields (`weekFriends`, `weekIdeas`, `weekCouples`, `weekEngagements`, and the day/month/all versions) one line each instead of five switch statements.

  **`CommunityService.totals` is two aggregate round trips, not one, because Firestore allows five aggregations per query and this needs six.** Both are still billed at roughly one read per thousand documents, so the split costs about one read. It also gained `where(actionsField, > 0)`, which is what makes "שדכנים פעילים" mean "did at least one thing" rather than "opened the app" — a member is written with the current period key at every publish, which is the same trap the leaderboard already had a `> 0` for. **That needs three new composite indexes** (`dayKey`+`dayActions`, and the week and month versions, all ascending) and `firestore.indexes.json` has them; the all-time version filters one field and runs on the automatic index.

  **The home screen has one activity block where it had two.** `HomeActivityPanel` and `HomeCommunityTaster` are deleted; `HomeActivityBlock` shows "הפעילות שלך" beside "פעילות הקהילה" with a שבוע/חודש/כל הזמנים switch and a link to the scoring sheet. Its own figure comes from `CommunityProvider.myPoints` (Gregorian, Israel-timed) rather than from a second local count, so the two columns are the same kind of week. The heading and the figures open `/activity`; the switch and the explanation link deliberately do not, so neither swallows the other's tap.

  `/activity` is now `הנתונים שלך` → `הפעילות שלך` (+ a personal-only Hebrew-month chart) → `פעילות הקהילה` → `דירוג השדכנים`, and the entry in `profile_screen.dart` is removed — the way in is the home block. The four all-time tiles open the existing `/stats/month/:metric` drill-downs and the chart links to `/stats/month`, so nothing was orphaned by taking the screen out of the settings.

- 2026-08-16: **The community layer is the first cross-user read in this app, and it was written for the read budget.** Three decisions carry it, none obvious from the outside.

  **One document per matchmaker, `communityMembers/{uid}`, holding every window at once.** Each count sits beside the key of the window it belongs to (`weekKey` + `weekActions`), and the keys are rolled over on write. A leaderboard cannot sort by a field that does not exist, so the counts have to be *stored*; without the keys, "is this row still this week's?" would be a client-side scan of the whole collection. Writes happen twice a session — app open and app pause, on `CloudSyncScheduler`, beside the cloud backup — never per action. Everything is *derived* from the local ledgers rather than incremented, so a double publish writes the same numbers again and a restored backup is correct.

  **Community totals are Firestore aggregate queries, never a read of the members.** `query.aggregate(sum(...), count(), …)` is billed at roughly one read per thousand documents matched, so the whole community area costs about four reads whatever the community's size. Summing client-side would have cost one read *per matchmaker, per refresh, per screen* — which is the thing the user specifically asked to avoid. The reader's own rank is the same trick: a `count()` of the rows above them, not a download of them.

  **Nothing refreshes on a rebuild.** `CommunityService` holds a process-level cache with a ten-minute deadline, shared by the home taster and the activity screen, and invalidated on publish. `firestore.indexes.json` is new and **must be deployed** — four composite indexes, one per window, on (`hidden`, periodKey, periodActions desc); the leaderboard query simply fails without them.

  **The count is now anti-inflatable, because it stopped being private.** `ActivityStats.countBetween` deduplicates through one set: a person by *name and day* (which covers an import run twice, a contact added twice, and a delete-and-re-add — the last of which returns with a new id, so nothing keyed on the id would catch it), an idea by its pair and day, and a status change by its target and day. Automatic moves were already excluded.

  **`CommunityProfileStore` and `CommunityPromptsStore` must never call `Box.put` directly.** They did, briefly, and it hung `Hive.close()` in `tearDownAll` for the entire widget-test suite — a `put` started inside the fake-async zone is never driven to completion. Both now write only through `persistHomeSetting` (root zone) and keep a `_pending` map so a value written this frame is readable in the same frame.

  Leaderboard privacy: `HideFromLeaderboardTile` is drawn in three places — the leaderboard itself, the activity screen and the settings — because a privacy control that only exists in a settings screen is one people find after they wanted it.
