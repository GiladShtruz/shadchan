# AGENTS.md

Guidance for future agents working in this repository.

## Project Snapshot

- This is a Flutter app named `shadchan`, a Hebrew RTL shidduchim management app.
- The current Dart source layout is intentionally simple and flat:
  - `lib/models/` - Hive data models and generated adapters.
  - `lib/providers/` - `ChangeNotifier` repositories for people and matches.
  - `lib/screens/` - top-level app screens and flows.
  - `lib/services/` - backup/import, contacts import, incoming files, notifications.
  - `lib/utils/` - routing, theme, enums, formatting, phone/share/name helpers.
  - `lib/widgets/` - reusable UI widgets.
  - `lib/dialogs/` - reusable dialogs and sheets.
- App entry points are `lib/main.dart` and `lib/app.dart`.
- Navigation is centralized in `lib/utils/app_router.dart` using `go_router`.
- Tests live under `test/`, with service tests in `test/core/services/` and the app boot test in `test/widget_test.dart`.

## Product Rules

- All user-facing UI text must be Hebrew.
- Keep the app fully RTL. `lib/app.dart` wraps the app in `Directionality.rtl`; new screens and widgets should fit that assumption.
- Preserve local-first behavior. User data is stored locally with Hive, local files, and explicit import/export flows.
- Be careful with privacy-sensitive features: contacts, photos, sharing, backup JSON files, and notifications.
- If a task is unclear or has a meaningful product/technical choice, ask before proceeding.

## Platform Rules

- Keep the minimum platform intent aligned to Android 21 and iOS 15.5 unless the user explicitly approves a change.
- iOS deployment target is set to `15.5` in `ios/Runner.xcodeproj/project.pbxproj` and in `ios/Podfile`. The floor is forced by the dependencies, not by choice: the Firebase pods require 15.0 and `google_mlkit_face_detection` requires 15.5. Both files must be changed together.
- iOS bundle identifier is `com.gilad.shadchan`, matching the Android `applicationId`. It is also the identifier the Firebase iOS app is registered under, so changing it means re-running `flutterfire configure`.
- `ios/Podfile` is hand-written (Windows `flutter create` never generates one). Its `post_install` block sets the permission_handler compile flags: only `PERMISSION_PHOTOS=1`, everything else `0`, so the binary carries no API references without a matching usage description in `Info.plist`. Adding a new `permission_handler` permission means adding both the flag and the plist string.
- Android uses the Flutter Gradle values in `android/app/build.gradle.kts`; do not raise the effective min SDK casually.
- Android release builds use `android/app/proguard-rules.pro` and `android/app/src/main/res/raw/keep.xml` for notification/Gson/R8 safety.
- Native file-open backup import is wired through:
  - Android: `android/app/src/main/kotlin/com/gilad/shadchan/MainActivity.kt` and `AndroidManifest.xml`.
  - iOS: `ios/Runner/IncomingBackupFileBridge.swift`, `SceneDelegate.swift`, and `Info.plist`.
- Share-into-app on iOS is the `ShareExtension` target (`ios/ShareExtension/`). It runs in its own process, so the share is handed over through the app group `group.com.gilad.shadchan` — `ios/Runner/SharedProfileInbox.swift` owns that layout and is compiled into *both* targets. The extension writes image files first and the `payload.json` manifest last; the app only reads directories that have a manifest, so a half-written share is never imported. The extension then opens the app with the `shadchan-share://` scheme. Changing the app group id or the scheme means changing both entitlements files, `SharedProfileInbox.swift`, and `Runner/Info.plist` together.
- The drafts the extension produces go through the *same* `shadchan/incoming_shared_profiles` channels as the Android `SEND` intents, in the same `{id, text, filePaths}` shape, so no Dart code is platform-specific.

## Development Workflow

- Read this file before starting work and update it after meaningful project changes.
- Prefer the existing folder structure before adding new layers.
- Keep generated Hive files (`*.g.dart`) in sync when changing Hive models/enums:
  - `flutter packages pub run build_runner build --delete-conflicting-outputs`
- Run targeted checks first, then broader checks when the change touches shared behavior.
- Useful verification commands:
  - `flutter analyze`
  - `flutter test`
  - `flutter build apk --debug`
  - `flutter build apk --release` for release/platform-sensitive changes.
- iOS native compilation is not normally verifiable from this Windows environment; mention that when relevant.

## Current Capabilities To Preserve

- People management: list, search/filter/sort, add/edit/detail, favorites, gallery photos, sharing, delete warnings.
- Matches management: list, create, duplicate detection, detail, status/handler updates, notes timeline.
- Dashboard tab at `/dashboard`.
- Contacts import: explicit permission-on-entry flow, search by name/phone, multi-select import, duplicate blocking by normalized phone.
- Unified add-contacts screen at `/people/import` with toggle between swipe (default) and list views; legacy `/people/swipe` redirects to it.
- Local JSON backup/export/import from Settings.
- Open-with-app backup import for JSON backups.
- Share-to-app intake for shidduch details from WhatsApp/other apps: Android accepts text, image, or image+text shares; iOS accepts image open-with through document handling. The flow asks whether to create a new person or add to an existing person, then opens `PersonFormScreen` with the shared text in `כרטיסייה לשליחה` and shared images staged as unsaved photos.
- Birthday notifications using local timezone support.
- Hebrew privacy policy screen and Settings entry.
- Optional Google Sign-In from the profile's `החשבון שלי` section, upgrading the anonymous Firebase account in place.
- Cloud backup to Firestore + Cloud Storage while signed in, running on app open and close, with an explicit additive restore. Covers people, matches, both note kinds, the matchmaker's own profile, and every photo file.

- 2026-08-14: **A proposal's status changes now have a record of their own.** New `lib/models/match_status_event.dart` (Hive typeId **15**, box `match_status_events`, adapter registered in `main.dart`) holds `{id, matchId, fromStatus, toStatus, createdAt, automatic}`. It exists because a status change was the only meaningful thing the app did that left nothing dated behind: `updatedAt` is overwritten by the next change and says nothing about what the change was, and the journal writes an automatic note for *some* transitions and not others. `ActivityStats` used to infer a status change from those notes and then drop person events within a five-second window as "the same act propagating" — two guesses, both now deleted. The count is arithmetic. **There are exactly three places a proposal's status is written** — `updateStatus`, `setWaiting`, `syncMatchesForPerson` — and all three call `_logStatusChange`; adding a fourth without it is the one way to make the figures wrong again, which is what `test/core/services/match_status_events_test.dart` (8 tests) guards. `automatic: true` marks the moves the app makes itself: one candidate going on a break pushes all their open proposals to "בהמתנה", and that is one decision about a person, not five about proposals — recorded as history, not counted as work. **The propagation the other way is solved by data, not timing:** `PersonRepository.updateProfileStatus` takes `causedByMatchId`, stamped onto the `PersonEvent`, and `markPersonBusy`/`markPersonMazelTov` now carry the proposal's id (their signatures changed to `(personId, matchId)`), so the two automatic "תפוס" events a dating couple produce point back at the proposal that caused them and are skipped by the count. The box is an **optional** third constructor argument to `MatchRepository`, mirroring `PersonRepository`'s event box, so a test that only needs proposals does not have to open a third box; without it nothing is logged and everything else behaves identically. - 2026-08-14: The cloud backup. **Hive stays the source of truth** — nothing in `lib/services/cloud_sync_service.dart` is ever read to answer a question the app asks during normal use, so the app behaves identically offline and a Firestore outage can slow a backup but can never show a stale candidate. The shape is one document per record under `users/{uid}/{people,personNotes,matches,matchNotes}/{id}`, not one blob: a blob would be rewritten in full for one edited note and would eventually hit the 1MB document ceiling. **Photos** are the thing the JSON export never solved — it stored file *paths*, so a restore on a new phone produced people with no faces. Files now go to Cloud Storage at `users/{uid}/photos/{basename}` and the documents carry basenames, rebuilt into local paths on the way down; a photo that will not download is dropped from the person rather than left as a path to a file that is not there. **Incremental by fingerprint, not by timestamp:** `lib/services/sync_state_store.dart` keeps an md5 per record in the `settings` box, because `PersonNote`/`MatchNote` are editable and carry only a `createdAt`, so an edited note is invisible to any watermark scheme. The map's keys are sorted before hashing, or a serializer growing a field in the middle would mark the whole database as changed. The ledger is a cache — losing it costs one full re-upload — and is dropped outright when the uid changes, since it describes a different account's tree. **Serialization is shared, not copied:** `BackupService`'s eight record codecs became public and `importData` was split into `importData(File)` + `importPayload(Map)`, so the file backup and the cloud sync cannot drift apart and the cloud restore inherits the same additive merge (existing ids never overwritten, a match dropped when either side is missing). **Triggers** are app open and close (`lib/widgets/cloud_sync_scheduler.dart`, on `resumed`/`paused` plus one post-first-frame run) rather than a watcher on every write, which would need a debouncer nobody can tune; the honest gap is that a change lost to a *crash* misses the cloud until the next launch, since `detached` is not delivered reliably. `paused` is used, not `detached`, for the same reason. **An anonymous account is refused a backup** in both `_requireAccount` and the rules — it dies with the install, so a backup under it could never be restored and writing one would be worse than not writing one. **Rules live in the repo** (`firestore.rules`, `storage.rules`, wired through `firebase.json`), close everything not explicitly named, and gate on `request.auth.token.firebase.sign_in_provider != 'anonymous'`; Storage additionally caps writes at 12MB and `image/.*`. **Test hazard, third instance of the family:** `SyncProvider` takes `enabled` for the same reason `AccountProvider` takes `connect` — `CloudSyncScheduler` fires from the app's own builder, so every widget test pumping `App` would otherwise reach `ensureReady` and hang on its deadline timer. **Deliberately not included:** the matchmaker's own profile (name, gender, personal card and its photos) lives in the `settings` box and is out of scope here, exactly matching what the JSON backup has always covered — a restore rebuilds the database, not the profile. Privacy policy updated in both `PRIVACY_POLICY.md` and `lib/screens/privacy_policy_screen.dart`; the old "nothing leaves the device" claim was true and is not any more. **Dependency pin, do not lift casually:** `firebase_core` is pinned to exactly `4.12.1` and `firebase_app_check` to exactly `0.4.5+2`. Adding Firestore pulled core up to 4.13.0, which changed a Kotlin signature App Check 0.4.5+2 calls; App Check 0.4.6 fixes that but needs a newer Firebase Android BoM than 4.13.0's 34.17.0 (its `FlutterFirebaseAppRegistrar` imports `InternalDebugSecretProvider`, which is absent, so the file drops out and every reference to it goes unresolved). Neither pairing compiles — the two must move together, and `flutter pub get` succeeds for both, so only an Android build catches it. `cloud_firestore` and `firebase_storage` sit at 6.7.1 / 13.4.5 because of that pin. **Console steps still outstanding:** create the Firestore database and the Storage bucket, then `firebase deploy --only firestore:rules,storage` — until the rules are published every sync answers `notPermitted`. Verified with `dart format`, full `flutter analyze` (only the 3 pre-existing dashboard warnings + 1 pre-existing test info), all 240 `flutter test` tests and `flutter build apk --debug`; the round trip against a live project is unverified from here.

- 2026-08-14: Google Sign-In, as the identity a cloud backup can be restored onto. Until now the only account was the anonymous one `FirebaseBootstrap` mints for App Check and the AI quota — a *device* identity that dies with an uninstall, which is fine for a per-device quota and useless for a backup. New `lib/services/account_service.dart` upgrades that same account through `linkWithCredential` rather than replacing it, so the uid survives and nothing already written under it needs a migration; `credential-already-in-use` is caught and turned into a plain `signInWithCredential`, because it means this Google account already has a Firebase account from another phone and signing into *that* one is exactly what a restore wants.
